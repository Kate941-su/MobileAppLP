# お知らせ記事の追加

記事は `news/<YYYY-MM-DD>-<id>.md` に 1 本ずつ置く。マージすると `/news`、`/<slug>/news`、`/news/<ファイル名>`、LP の「お知らせ」欄（最新 3 件）、`/news/feed.xml` に反映される。

## 1. 何の記事かを決める

- 対象アプリ（`src/content/site.ts` の `apps` の slug）とバージョンをユーザーに確認する。サイト全体の話なら `app` は書かない
- アプリのリポジトリの場所:

  | slug | リポジトリ | バージョンの場所 |
  |---|---|---|
  | `dopadatsu` | `~/dopadatsu`（Flutter 本体は `dopadatsu/dopadatsu/`） | `pubspec.yaml` の `version` |
  | `data-holder` | `~/data-holder` | `pubspec.yaml` |
  | `stacklens` | `~/stacklens` | `pubspec.yaml` |

- **ストアで公開済みかを確認する**。審査中・段階的公開の途中なら、記事を書いても公開日（`date`）はストアで配信が始まる日にし、マージはその日以降にするようユーザーに伝える。未公開の機能を先に告知しない

## 2. 変更を調べる

- 比較範囲の決め方と変更の分類は **release-notes スキル（`~/.claude/skills/release-notes/SKILL.md`）の 1・2 に従う**（前回リリースのタグ → 今回、コミットだけでなく diff で動作を確認、利用者に見える変更だけを拾う）
- そのリリースのストア用リリースノートが既にあれば、それと矛盾しないように書く（記事はリリースノートの詳しい版）
- プラットフォームで挙動が違う機能（例: Android 先行）は、記事にもそう書く

## 3. 書く

[template.md](template.md) をコピーして埋める。

**front matter**（間違えるとビルドが止まる）

| キー | 必須 | 内容 |
|---|---|---|
| `title` | ○ | 「ドパ脱！ 1.2.0 を公開しました」「〇〇ができるようになりました」など。誇張しない |
| `date` | ○ | `YYYY-MM-DD`。ファイル名の日付と同じにする（ストアでの配信開始日） |
| `app` |  | アプリの slug。省略でサイト全体のお知らせ |
| `category` | ○ | `update`（アップデート全般）/ `feature`（目玉の新機能 1 つを紹介）/ `info`（それ以外のお知らせ） |
| `version` |  | `1.2.0` など。記事に表示される |
| `summary` | ○ | 1〜2 文。一覧・RSS・OG の説明に出る |
| `image` |  | 記事の先頭に出す画像（`public/news/<ファイル名>/` に置く） |

**本文**
- 冒頭 1〜2 文で何が変わったか。そのあと `## 見出し` ごとに 1 機能（何ができるか → 使い方 → 無料か Pro か）
- 「です・ます」。release-notes スキルの文面ルール（技術用語・クラス名を書かない、実装した事実だけ、効果を断定しない）に従う
- アプリ固有の表現の制約を守る（ドパ脱は医療的な効果をうたわない、性的な言葉・「NoFap」を使わない など。各アプリの SPEC / CLAUDE.md を確認）
- 画像: アプリのリポジトリのストア用スクショ（`fastlane/screenshots/ja`、`store/play/ja` など）や、ユーザーが用意した画面を `public/news/<ファイル名>/` に置き、本文から `![説明](/news/<ファイル名>/01.webp)` で参照する。1 枚 500KB 以下を目安に縮小（`sips -Z 1200`）
- リンクはサイト内なら `/dopadatsu` のような相対パス
- 生の HTML は出力されない（Markdown だけで書く）

## 4. 確認して PR

1. `git branch --show-current` を確認し、`main` なら `news/<ファイル名>` ブランチを切る
2. `npm run build`（front matter の誤りはここでエラーになる）→ `npx next start` で `/news/<ファイル名>` と LP の「お知らせ」欄を目視
3. ユーザーに本文を見せて確認をもらう（**根拠にしたコミットの一覧**と、書かなかった変更も添える）
4. コミット → push → PR。マージ（＝公開）はユーザーが、ストアでの配信開始後に行う
